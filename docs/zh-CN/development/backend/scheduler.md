# 可恢复的后台刷新队列

队列将每个订阅源刷新放入独立 PHP 子进程。任务状态存在 `DATA_PATH/scheduler/queue.sqlite`，文章仍使用原有 SQLite、MySQL 或 PostgreSQL 数据库。每个子进程退出时释放解析器、扩展和正文占用的进程内存。

默认关闭。启用后，原有 `app/actualize_script.php` 定时入口改用队列；不需要另加一份周期任务。网页手动刷新、WebSub 和 `cli/actualize-user.php` 仍保留原有入口，共用订阅源文件锁，不经过队列全局配额。

## 使用

在 `data/config.php` 中加入或调整：

```php
'scheduler' => [
    'enabled' => true,
    'workers' => 2,
    'per_user' => 1,
    'per_host' => 1,
    'worker_memory_mib' => 128,
    'job_timeout' => 180,
    'kill_grace' => 5,
    'lease_seconds' => 240,
],
```

```sh
php cli/refresh-queue.php schema   # 配置定义、默认值与单位
php cli/refresh-queue.php status   # 排队、运行、重试及有界历史
php cli/refresh-queue.php enqueue  # 根据当前用户与订阅设置同步任务，不抓取
php cli/refresh-queue.php run      # 同步任务并运行当前到期工作
php cli/refresh-queue.php pause    # 持久暂停领取新任务，现有任务继续
php cli/refresh-queue.php resume   # 恢复领取；另行执行 run 才会启动调度器
```

显式执行 `run` 不要求 `enabled=true`，便于一次性试运行；`enabled` 只决定标准定时入口是否转交队列。命令结束后不会保留调度服务。`run_seconds` 到期后不再领取新任务，已经运行的子进程仍会被等待或按单任务超时终止。

暂停状态保存在队列数据库中，重新执行 CLI 不会自动解除。暂停不删除任务，也不撤销正在运行的租约。向当前调度进程发送一次 `SIGTERM` 或 `SIGINT`，只停止该进程继续领取任务并等待现有任务结束；再次发送任一信号，立即终止它自己启动的工作进程，未完成任务保留为可重试状态。进程信号不改变持久暂停开关。

配置定义的唯一来源是 `FreshRSS\Services\Refresh\SchedulerConfiguration::schema()`。未知字段、错误类型及不合法的组合直接报错，不悄悄采用另一套值。管理员可从 Reader 的 `scheduler` GET API 查看有效配置和运行记录；该 HTTP 接口不会启动子进程。

## 并发、租约与锁

- SQLite 使用 WAL 和短的 `BEGIN IMMEDIATE` 事务领取任务，领取时同时检查全局、域名和用户配额。
- 每个任务得到随机所有者标识。过期进程不能确认或删除新进程已经领取的任务。
- 工作进程另持有全局、主机和用户执行槽的 `flock`。即使父进程意外退出、租约过期，仍存活的工作进程也不会被其他队列进程突破执行配额。
- 订阅源锁也改为进程持有的 `flock`，不再按“一小时”删除锁文件；正常退出和异常进程结束都释放内核锁。
- 锁文件保留在磁盘，不用删除它们表示“解锁”，避免两个进程锁住不同 inode。迁移到新版本前应停止旧版本的轮询进程；旧版基于文件存在性的锁无法与新锁混跑。

`per_user` 默认值为 1，保持原有单用户任务顺序。设为 2 或更大时，同一用户可以并发下载不同订阅源，但应用文章过滤、跨订阅重复标题规则、暂存文章提交、自动标签及计数更新仍由用户写入锁串行执行。每用户维护任务与该用户的下载任务互斥。SimplePie 初始化前后 hook 的调用单独持有同一用户锁；这些 hook 自己执行网络请求时仍会占用串行区间，不能保证启用任意插件后的下载加速。

传统 `actualizeAction()` 也保留锁对象直到本次入库和计数处理结束，异常时回滚自行开启的事务后释放锁。传统入口并不全都使用新的配置写入协议，也不经过队列的全局并发配额，因此不能把队列锁描述为所有网页、插件和后台写入之间的完整互斥。

`per_host` 按订阅 URL 的原始主机名分组，不等同于重定向目标、全文提取站点和插件自行访问的所有主机限流。PHP 插件仍为受信任的进程内代码。运行过程中更改并发数，应在当前 CLI 执行结束后启动下一轮，使所有工作进程采用同一组配额。

## 失败处理与维护

普通失败使用指数退避及可配置抖动，不删除任务。退避不会被下一次 `enqueue` 覆盖；HTTP `Retry-After` 要求更晚重试时，采用更晚时间。已静音或删除的订阅、禁用和不活跃的账号不会再产生新的普通刷新任务。每次同步还清理这些对象的未运行任务。

父进程以单调时钟计算经过时间和任务截止时间，先发送 TERM，经过 `kill_grace` 后发送 KILL，只终止自己创建的子进程。数据库暂时不可用导致确认失败时，租约过期后可以再次领取。子进程在加载应用和插件前还设置 PCNTL 内核闹钟，采用默认终止动作，在超时与宽限之和到达时自行结束；父进程被直接终止后，这个截止时间仍然有效，执行槽随后由内核释放。租约只恢复任务状态，不负责终止进程。`poll_ms` 是检查子进程的最大等待时间；临近超时或终止宽限截止点时会主动缩短等待。

维护使用单独任务：每用户执行轻量数据库维护、已暂存文章提交、计数更新、用户维护 hook 和动态 OPML；共享任务清理过期缓存及 Retry-After 文件。队列正常刷新不再触发 `actualizeFeedsAndCommit()` 内的随机缓存清理。其他旧入口和 HTTP 缓存路径保留既有清理策略。

已暂存文章提交、标签写入及计数刷新失败会向上报告，避免被记录为刷新成功。可重试意味着可以重复执行；不会承诺插件文件、网络或外部服务副作用的精确一次执行。

历史仅存用户、订阅 ID、任务类型、结果代码、耗时和 PHP 峰值内存；不存订阅完整 URL、认证信息或文章正文。`peak_bytes` 是 PHP 报告的分配量，不是操作系统 RSS，也不包含所有原生库内存。

## 配置语义

| 字段 | 默认值 | 含义 |
| --- | --- | --- |
| `workers` | 2 | 队列全局并发工作数 |
| `per_user` | 1 | 每用户并发源下载数，应用与入库仍串行 |
| `per_host` | 1 | 同原始主机并发数 |
| `worker_memory_mib` | 128 | 每个子进程 PHP 内存上限，MiB |
| `job_timeout` / `kill_grace` | 180 / 5 | 单任务墙钟预算及终止宽限秒数 |
| `lease_seconds` | 240 | 必须大于前两项之和 |
| `run_seconds` | 300 | 本次停止领取新任务的时间；0 表示无此截止时间 |
| `retry_base` / `retry_max` | 60 / 21600 | 重试起始、最大退避秒数 |
| `retry_jitter_percent` | 20 | 退避随机增量百分比，0 禁用，最多 100 |
| `maintenance_interval` | 3600 | 独立维护周期，秒 |
| `websub_poll_interval` | 86400 | 活跃 WebSub 源的后备轮询周期，秒 |
| `history_limit` | 1000 | 保留完成记录数量，0 不记录 |
| `status_history_limit` | 100 | 状态响应每页历史数；0 不展示历史但不清除保留记录 |
| `history_days` | 7 | 历史年龄上限，0 仅按数量限制 |
| `busy_timeout_ms` | 5000 | 队列 SQLite 写锁等待预算，毫秒 |
| `poll_ms` | 200 | 父进程检查子进程的最大等待间隔，毫秒 |
| `plan_batch_size` | 128 | 规划时每页订阅数及每次队列写入事务的任务数 |

规划按递增订阅 ID 分页读取，按 `plan_batch_size` 分批提交队列写入，并复用入队语句。连接内临时表记录已看到的订阅 ID，完整扫描结束后才删除已不存在或静音的待运行任务；扫描中断时不据此清理旧任务。独立规划文件锁阻止同一实例的两个规划器同时扫描和清理。

状态响应中的 `history` 按历史 ID 降序返回，`historyNext` 为下一页游标；管理员 Reader `scheduler` GET API 接受 `history_before` 参数继续翻页。CLI `status` 返回第一页。历史保留量由 `history_limit` 与 `history_days` 控制，每页返回量由 `status_history_limit` 控制，二者分开配置。`oldestDue` 为当前可领取待办任务中最早的到期时间，没有到期任务时为 `null`；暂停状态下这些任务仍保留并可出现在统计中。

订阅自己的 TTL、HTTP 缓存和 WebSub 语义仍存在。全文提取仍在对应刷新工作进程中执行，尚未拆成独立文章任务；慢解析会占用该任务的预算。

队列需要 PDO SQLite、PCNTL、`proc_open` 和可写的本地数据目录。当前测试使用 Linux 本地文件系统；未验证 NFS、分布式多节点和 Windows。不要将 SQLite 队列文件作为多主机共享队列使用。

## 已执行的检查

单元回归包括多进程同时领取、全局/主机/用户限制、过期所有者拒绝确认、重试保持、任务清理、历史上限、进程被 KILL 后释放执行槽。完整子进程链路可用下面的测试重现：

```sh
python3 tests/integration/refresh/scheduler_test.py --php php
```

测试自行创建临时 DATA_PATH、SQLite 数据库与本地 HTTP 服务，覆盖正常 RSS 入库、慢源超时、HTTP 500、重复运行不绕过 TTL/退避、恢复后成功重试，以及 CLI 退出后无遗留子进程。没有访问真实订阅或生产数据库。

同一集成测试还在慢源工作进程已经进入 HTTP 请求后，仅对父调度进程发送 `SIGKILL`。实测子进程约 2.99 秒后由自身 `SIGALRM` 终止，执行槽与订阅源锁均释放；等待实际租约到期后，新调度进程重新领取任务并成功入库。测试进程接管并回收孤儿进程，确认退出信号，不把已退出的僵尸进程误计为仍在运行。

同一用户并发抓取及在途配置修改可另外运行：

```sh
python3 tests/integration/refresh/concurrency_test.py --php php
```

本地四个各延迟一秒的源，`per_user=1` 实测总耗时 5.572 秒、源请求峰值为 1；`per_user=2` 为 2.973 秒、峰值为 2。两组最终均入库四篇文章，同分类重复标题规则留下一个未读项，四篇文章全部正确加上自动标签，缓存计数一致且暂存表为空。这些数字仅反映该本地测试服务及 PHP 进程启动开销。

测试还在 HTTP 请求进行期间修改订阅 URL、名称和属性，确认旧的成功响应不写入文章，旧的 `410 Gone` 响应不禁用新配置；重试只采用修改后的 URL。

持久暂停、恢复和进程信号控制可运行：

```sh
python3 tests/integration/refresh/control_test.py --php php
```

该测试确认 `pause` 允许已经运行的任务正常完成，后续 CLI 仍停止领取；`resume` 后剩余任务继续执行。单次 `SIGTERM` 仅停止当前调度器领取新任务并等待现有任务；第二次终止信号实测在 0.11 秒内终止子进程，任务保留为可重试状态。另在 `poll_ms=10000`、`job_timeout=1`、`kill_grace=1` 下，慢任务实测总计 2.13 秒结束并记录为超时，长轮询间隔没有延长任务时限。

控制测试还保留了“不匹配任何自动标签规则”的正常文章，确认空标签集合不会被误判为数据库写入失败。

传统刷新入口的锁生命周期可单独复现：

```sh
python3 tests/integration/refresh/legacy_test.py --php php
```

测试调用真实 `actualizeAction()`，并在 SQLite 事务开始、提交和回滚边界启动另一个 PHP 进程尝试获取用户锁。正常提交、`noCommit` 保留暂存文章和触发器注入提交失败三条路径均确认锁在事务处理期间仍被持有，action 结束后已释放；失败时文章保留在暂存表，连接不遗留未完成事务。

并发源测试还覆盖队列记录的主机与当前订阅主机不一致时，跳过所有刷新 hook 和 HTTP 请求，包括图标请求；主机重新匹配后才抓取并入库，避免配置变动绕过领取任务时的主机配额。
